# OTA rebuild — 2026-09-03

David: *"Ota has never worked. Can you design a plan to fix it."*

## What the telemetry actually said

It **had** worked — 60 sessions downloaded a bundle and committed it, and one
device walked `d2d10d06 → c02ae379 → bbd617c2 → 5795b6cf`. The server pipeline
audited 6/6 green. So "never worked" was the wrong frame, and chasing it as a
transport problem would have missed all three real defects, which lived in the
**response contract** of `api/ota/manifest.ts`.

The `47%` download-failure rate quoted on 2026-09-02 was itself wrong: 57% of
those failures were generated by our own endpoint.

### 1. We reported every no-op as a failure (72 of 127)

The no-update reply was `{version, url:''}` with no `kind`. The plugin's own
source — `CapacitorUpdaterPlugin.swift: normalizedUpdateResponseKind` — maps a
**missing** `kind` to `"failed"`, then fires `downloadFailed` **and** a
`download_fail` stat before firing `noNeedUpdate`. Signature in PostHog: an
`ota_download_failed` whose `to` equals `running`, immediately followed by
`ota_no_need_update`.

### 2. It could roll devices BACKWARD — the serious one

Version comparison was string **equality** only. Nothing stopped a stale pointer
serving an older bundle. On 2026-08-31 a device running `d2d10d06` (the Aug 28
release) was handed `c02ae379` (Aug 5) and applied it. That is how devices ended
up stranded on the Aug-5 bundle carrying the iOS WASM crash — they were not
failing to update, OTA **pushed them onto the crash and held them there**.

Contributing cause: only `daily-deploy.yml` published, once a day, behind two
gates. Every other push to main deployed the web and published nothing, so the
pointer routinely sat weeks behind main.

### 3. 41 MB to deliver a 200 KB fix

`public/data` is 92 MB raw — `openings-masters-db.json` 36 MB,
`saintlouis-teachings.json` 24 MB, `corpus-spoken.json` 13 MB — files that
essentially never change. The download is foreground-only and restarts from zero.

| download outcome | median session | p90 |
|---|---|---|
| succeeded | 548s | 3842s |
| failed | 240s | 294s |

Essentially no failing session lasted past 5 minutes. Casual users could not
finish it; the heaviest user could.

## What shipped

Ordered deliberately: **safety before reliability.** A more reliable OTA in
August would have pushed *more* devices onto the crash bundle, faster.

1. **Forward-only.** Every bundle publishes a monotonic `ordinal` (commit
   timestamp). The guard lives at the **write** (`publish-ota-bundle.mjs` refuses
   to move the pointer to an older commit; `OTA_PUBLISH_FORCE=1` overrides) and
   again at the **read** (the endpoint refuses to hand back a bundle at or below
   the ordinal the device runs). `pin` in the pointer is the deliberate-rollback
   escape hatch, and serves the pinned bundle's **own** url.
2. **`kind: 'up_to_date'`** on every no-op path.
3. **Delta updates.** The endpoint returns `manifest: ManifestEntry[]`
   (`{file_name, file_hash, download_url}`, SHA-256 hex of raw bytes), honoured
   by the autoUpdate flow at `CapacitorUpdaterPlugin.swift:3747`. Files are
   uploaded content-addressed to `ota/files/<sha256>`, so an unchanged file is
   never re-uploaded. The plugin **tries the builtin bundle first**
   (`CapgoUpdater.swift:1178`), so even a fresh App Store install copies the
   92 MB locally and downloads only what changed. No Capgo cloud account.
4. **Version-stamp guards.** The endpoint collapses the 7-vs-8-char SHA split
   (legacy devices were offered a permanent update to the commit they already
   ran); `ci_post_clone.sh` now hard-fails if `OTA_BUNDLE_VERSION` is empty or
   not an 8-char SHA (a real device reports `builtin: "1.0"` from that miss).
5. **One publisher, every push.** `.github/workflows/ota-publish.yml`, own
   concurrency group. The step in `daily-deploy.yml` was removed — two publishers
   racing is how a superseded dist reaches devices.
6. **Redis/Blob divergence.** `readLatest` now prefers whichever store holds the
   newer ordinal instead of Redis unconditionally (a stale Redis value would pin
   every device to an old bundle — the same rollback through the back door).

## Decisions

| date | decision |
|---|---|
| 2026-09-03 | Rollback policy: forward-only by default, `pin` for deliberate rollbacks. |
| 2026-09-03 | Cadence: auto-publish on every main push. Safe *because* of forward-only + the existing `notifyAppReady` auto-revert. |
| 2026-09-03 | Delta ships behind `OTA_DELTA` (`off`/`canary`/`on`, default **canary** = David's devices). The delta path cannot be proven from CI, only on a real device, and a broken delta means a device silently stops updating. Recovery is one env var, no deploy. |

## Open / next

- [ ] **Flip `OTA_DELTA=on`** once the canary shows `ota_download_complete`
      followed by `ota_app_ready` on a delta offer. Until then everyone else gets
      the whole-zip path, i.e. today's behaviour.
- [ ] **`ota/files/` GC.** Content-addressed blobs accumulate. Not urgent and not
      the per-event write pattern that once paused the account, but it needs a
      periodic sweep keyed on the last N manifests as retention roots. Never
      delete during a publish — a device mid-download would lose its files.
- [ ] **`ota_boot` under-reports** — 6 devices vs 56 for `ota_app_ready`. The
      boot snapshot is emitted from `startOtaObserver` early in `main.tsx`,
      likely before analytics is initialised, so most are dropped. It is the most
      decisive per-launch signal (running vs builtin) and it is mostly missing.
- [ ] `android-play.yml` still defaults to a stale `'3.2'` version.

## Does this remove Apple reviews?

For anything in the web bundle — coach logic, narration, lessons, content, UI, JS
fixes — yes. Not for native code, plugin changes, permission strings, the icon,
the marketing version, entitlements, or store metadata. Permitted under the
interpreted-code clause (old §3.3.2, now §3.3.1(B)); the line is that it must not
change the app's advertised purpose.
