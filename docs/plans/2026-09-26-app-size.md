### Corrections to what I told David earlier today
- I said delta OTA "was never turned on." **Wrong.** It shipped 2026-09-03, was turned **on for everyone** (commit `9ff63f84`, measured 8 MB instead of 41 MB, every hash verified), and at some later point the pointer was set back to `off`. Nothing in the repo records who or why.
- I said the entry chunk was 5.1 MB. It is 5.26 MB today, but the one live OTA devices got was **8.6 MB** (pages were still inside it then).
- **New root cause found:** every build renames **142 JS files (8.7 MB)** even when no code changed. The build id `<sha>+Date.now()` is baked into `appAuditor.ts:997`, which sits in the entry chunk, and 131 chunks import the entry by its hashed name. So even with delta on, a docs-only OTA ships 8.7 MB.

## 1. The API-key question
An API key built into an app is not a secret (anyone can pull it out of the IPA), and this data is not secret either — the web app already serves every file openly. So: **no key**. Serve the files from the web origin (Vercel CDN), which is what already happens on the web. Verified from a `capacitor://` origin: 200, `access-control-allow-origin: *`, brotli, `max-age=86400`.

## 2. The fixes — what each does, what David will feel, what could break

### Fix A — Turn delta OTA back on (the biggest, cheapest win)
- **Does:** each update downloads only changed files instead of the whole 35 MB zip. Measured when it was last on: 14 of 1,967 files fetched.
- **Code needed first:** (1) a `delta` flag on the client's OTA telemetry so we can see which path each device took — today PostHog cannot tell them apart; (2) the build-id fix (Fix C), otherwise every update is ~8.7 MB raw / 2.6 MB wire instead of a few hundred KB.
- **Switch:** `node scripts/ci/ota-set-delta-mode.mjs canary` (David's 3 devices) → dispatch one OTA → David confirms on his phone → soak 2 publishes → `on`. Rollback is the same script with `off`, effective on the next update check, no deploy.
- **You'll feel:** updates land in seconds instead of minutes. App speed unchanged.
- **Risks (real, from the plugin source):**
  - If ANY one file fails, the whole version is marked ERROR on that phone and it will not retry that version (`CapacitorUpdaterPlugin.swift:3760`). It recovers at the next publish. The zip path has the same sticky-error rule, so this is not new — but delta has no resume.
  - Each file must finish in **25 s** (`responseTimeout: 20` + 5). The 2.5 MB compressed entry chunk needs ~0.8 Mbps. Weak cellular could miss that. Mitigation: shrink the entry chunk (Fix E) and raise `responseTimeout` to 60 in the next iOS build (native setting — needs a TestFlight/App Store build).
  - `ota/files/` on Blob grows ~9 MB per publish, never cleaned. Add a sweep that keeps files referenced by the last N manifests (separate small job).
- **Open question for David:** did you (or a session) turn it off on purpose? If there was a failure behind it, I want to know before re-enabling.

### Fix B — Stop shipping unused chess engines to iOS
- **Does:** removes `stockfish-18-lite*` (multi + single WASM, 14.4 MB) and the dead `sf16-7.*` + `lila-bridge.worker.js` (0.46 MB) from the iOS app and the iOS OTA. Keeps `stockfish-asm.js`.
- **Proof it is safe:** routing in `stockfishEngine.ts:141, 222-229, 732-742` — iOS always gets the native Swift engine, falling back to asm; the analysis pool gets asm (`gameAnalysisService.ts:694`). PostHog, native, 90 days: **ios-native 99 devices, asm 7, multi/single 0.** The last WASM load on iOS was the 2026-09-02 crash storm, since fixed.
- **Where:** one `rm` line after `npm run build` in `ios/App/ci_scripts/ci_post_clone.sh` (and `setup:ios`), and the same line before the publisher in `.github/workflows/ota-publish.yml:122`, plus an assert that `stockfish-asm.js` survives. The web deploy builds separately on Vercel, so it keeps every engine. `sf16-7`/lila are dead on the web too — drop them from `stockfish:copy` and retire the stale `e2e/stockfish-ios-fix.spec.ts` lila check.
- **You'll feel:** nothing. Chess strength and speed identical — those files are never loaded on iPhone.
- **Size:** −14.9 MB on the phone, **−~11 MB of the download**.
- **Risk:** the OTA endpoint doesn't check platform. An Android app on OTA would lose its engine. There are **0** native Android users (PostHog, 30 days), but add a platform guard to `api/ota/manifest.ts` before Android ever ships.

### Fix C — Stop the build id from renaming 142 files every build
- **Does:** moves the build id out of the JS (emit it into `index.html` as a meta tag / `window.__BUILD_ID__`; `appAuditor.ts:997` reads it from there).
- **You'll feel:** nothing directly; it makes every delta update smaller (a no-code OTA → 0 JS files).
- **Risk:** none to chunking; `index.html` changes every build already.

### Fix D — Take the big data files off the phone (David's idea, sharpened)
All loaders already fetch on demand and already degrade to "say nothing" when a file is missing — never to wrong teaching. So the change is WHERE the fetch goes on iOS, plus keeping the result.

**Step D0 — delete what's dead (no user effect, helps web too):**
- `corpus-spoken.json` 13 MB → **~2.3 MB**. 50,000 of its 61,000 entries belong to creators deleted from `corpora.json` on 2026-09-21; nothing reads them.
- `saintlouis-teachings.json` — orphaned, no consumer in `src/`.
- `pro-game-references.json` is re-downloaded on **every boot** even though it's already stored in Dexie; hydrate from Dexie instead.

**Step D1 — one `dataUrl()` helper.** On native, `/data/x.json` → `https://chess-academy-pro.vercel.app/data/x.json`. (There are already six hand-copied native-URL helpers — this becomes the one, and the others can fold into it.)

**Step D2 — per file:**

| file | size (raw → wire) | how it's used | plan | what you'll feel |
|---|---|---|---|---|
| openings-masters-db | 36 MB → 3.5 MB | lookup by position (FEN), whole file loaded into RAM | **split into ~256 small shard files by position** on the CDN; fetch the shard for a position, keep it in Dexie | first lookup of a new position: one ~15-30 KB fetch (~0.2-0.5 s on wifi); after that instant. **Less RAM** (today the 36 MB parse is why Learn already skips this file on iOS). Offline: masters stats go quiet on positions never seen. Coach chat, review, play all still look it up. |
| danya-play-db | 6.2 MB → 1.1 MB | lookup by position | same shards | same as above |
| voiced-teachings | 4.7 MB → 0.54 MB | the ONLY exact-position teaching source (Watch/teach lessons) | download once in the background right after first launch, store in Dexie; the teach lesson waits for it if it isn't done | first-ever lesson on a fresh install may wait ~1-3 s. After that identical to today. **Alternative: keep it inside the app** — it's only 0.54 MB of download. My pick: **keep it bundled**; it's the heart of lessons and not worth any risk. |
| corpus-spoken (after prune) | 2.3 MB → ~0.7 MB | spoken rewrite of notes, loaded whole | download once, keep | none (falls back to the original note text for a second if missing) |
| danya-floating | 6.8 MB → 1.9 MB | notes matched by opening name/concept (drills, endgame, chat) | download once in background, keep | tactics-drill / endgame notes appear once it's downloaded (seconds on first launch) |
| pro-game-references | 2 MB → 0.4 MB | player game lookups | download once, keep (Dexie already holds it) | none |
| master-puzzles | 1 MB → 0.3 MB | Master Level puzzles, already seeded into Dexie | point at CDN | first open of Master Level needs a connection once |
| danya-review-openings | 96 KB | review sidecar | keep | — |

**Why shards, not a server endpoint or the live Lichess explorer:** the live explorer rate-limits and returns different data (W/D/L) than the local DB, so answers would change; a server function would have to load a 36 MB file on cold start. Static shards on the CDN give the **same data as today**, cost nothing per lookup, cache forever, and need no server.

**Sync callers need a prefetch.** `openingGenerator`, `coachFeatureService` (review) and `reviewStrategicOrientation` read the masters/his-play DBs synchronously. Before building a review or lesson, fetch the shards for that game's positions in parallel (a review already takes 45-90 s of engine analysis; this runs alongside it). Then `mastersMovesSync` reads the cache.

**Order that can't break old phones:** ship the `dataUrl()` + shard code FIRST (it works whether or not the files are still in the app). Only after that is live everywhere, strip `dist/data` from the iOS build and the OTA publish (same two places as Fix B). Keep the files in the repo and the web deploy — 30+ tests and ~36 scripts read `public/data` off disk.

- **Size:** ~−67 MB on the phone, ~−12 MB of the download.
- **Offline, first launch:** some notes/stats are quiet until the phone has been online once. The chess engine, lessons (with voiced bundled), puzzles and play all work offline as today.

### Fix E — Shrink and stabilise the main code file
- **Does:** move leaf data out of the entry chunk into its own chunks — lesson scripts (2.2 MB, 104 files that import only types/JSON/chess.js), the inlined JSON (0.49 MB: punish-gems, anti-openings, endgame, mating patterns…), `openingWalkthroughs`, and `openai`/`@capacitor` into vendor. Entry 5.26 MB → ~2.4 MB.
- **You'll feel:** nothing on speed — those chunks still load at boot (`index.html` preloads them). Updates get smaller because content chunks only change when content changes.
- **Risk:** Rollup may put a shared helper into a data chunk and create an import cycle (a boot crash). Gate: a test that no `appdata-*` chunk imports the entry.
- **Optional, later:** an import map so importers don't carry the entry's hash (cuts the remaining ~3.45 MB cascade). And lazy-loading `coachApi` + the lessons registry — the only item that also makes **boot faster**, but it makes `getLessonScript` async across five callers. Separate change.

### Fix F — The 17.5 MB of legacy auto-annotations
- 1,889 chunks from `src/data/annotations/*.json`, used only by the legacy `WalkthroughMode`/Drill/Train fallback for the ~3,000 DB-only openings (CLAUDE.md G9.3 already bans them as masterclass narration).
- **Option 1:** fetch them per opening from the CDN on demand (same `dataUrl()`): −17.5 MB on the phone, the legacy walkthrough needs a connection the first time per opening.
- **Option 2:** leave them. **David's call** — I lean Option 1.

### Fix G — `appdata-puzzles` (4 MB, loaded at every boot)
- 10 modules import `puzzles.json` synchronously. Converting it to fetch-and-store makes **boot faster** on every phone but is the biggest refactor here. Later phase, optional.

## 4. What does NOT change
- Chess engine strength and speed (iPhone uses the native engine, as it does today).
- Narration speed: the voice path (`/api/tts`, Google) is untouched; lesson notes stay on the phone (voiced bundled) or are stored after first download.
- Database lookups: masters + Danya lookups keep working with the same data; the first lookup of a new position takes one small network fetch, then it's stored.
- The web app: stays permanently unlocked and keeps every file.
- RAM: goes **down** (no more parsing a 36 MB JSON on the phone).
